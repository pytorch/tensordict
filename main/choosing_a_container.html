Which container should I use?#

Most code needs one of two forms of the same container. Use a TensorDict, the dict form, when your program chooses the keys at run time. Use a TensorClass, the class form, when you know the fields in advance and want methods on them. Both forms have the same tensor operations, and from_tensordict wraps the dict form in the class form without a copy:

>>> import torch
>>> from tensordict import TensorClass, TensorDict
>>> td = TensorDict({"pos": torch.zeros(4, 3), "vel": torch.zeros(4, 3)}, batch_size=[4])
>>> td["mass"] = torch.ones(4)  # add a key at run time
>>> class Particles(TensorClass):
...     pos: torch.Tensor
...     vel: torch.Tensor
...     mass: torch.Tensor
>>> particles = Particles.from_tensordict(td)  # wraps td
>>> particles.pos += 1  # writes to td
>>> td["pos"][0]
tensor([1., 1., 1.])

from_tensordict raises ValueError if the tensordict has a key that is not a field. to_tensordict() returns the data in the dict form, as a copy.

The other containers are special cases: items of different shapes, data on disk or on a server, and typed fields on a TensorDictBase. All the containers except the plain dict have a batch size: the leading dimensions that all their entries share (see Batch size, shapes, and indexing). Indexing, reshaping, and stacking apply to these dimensions.

The containers#

Container

Use it for

Main constraint

TensorDict

Tensors that share their batch dimensions, under string keys or nested keys that you add and remove at any time. The data is in memory, on any device.

Each entry must start with the batch dimensions. Any other value raises RuntimeError: batch dimension mismatch.

TensorClass

A fixed set of fields that you declare like a dataclass, with attribute access, your own methods, and plain Python values for fields that are not tensors.

It is not a TensorDictBase or a Mapping: tc["key"] and **tc raise ValueError, and a function that tests isinstance(x, TensorDictBase) rejects it.

LazyStackedTensorDict

A stack of tensordicts whose entries have different shapes, for example sequences of different lengths. lazy_stack() makes one. It keeps the stacked tensordicts, so a write to the stack changes them.

Each read of an entry stacks it into a new tensor. An entry with different shapes raises RuntimeError unless you ask for a padded tensor, a nested tensor, or a list (get(key, as_padded_tensor=True)). keys() lists only the keys that all the stacked tensordicts have.

PersistentTensorDict

Data in an HDF5 or Zarr file, read on demand. The file can be larger than the memory.

Each read loads a new tensor from the file, so an in-place operation on that tensor does not change the file. The in-place methods of the tensordict, such as add_() and update_(), write to the file when it is open for writing (mode="r+"); from_h5() and from_zarr() open it read-only by default. Needs h5py or zarr.

TensorDictStore

Data on a Redis, Dragonfly, or KeyDB server, which several processes or machines can read and write.

Needs a running server and the redis package. Each read goes over the network. The data stays on the server until you call clear_redis().

TypedTensorDict

Declared fields on a class that is a TensorDictBase, with **state unpacking and the full tensordict API.

Experimental: its API can change in a minor release without a deprecation cycle (see TypedTensorDict). Attribute access returns a string field as a NonTensorData wrapper. No custom __init__ and no __post_init__.

A plain dict of tensors

Any Python values, with no rule on their shapes.

No batch dimensions: you write a loop, or a torch.utils._pytree.tree_map call, for each operation on the values.

On PersistentTensorDict and TensorDictStore, use set_() for each key, or update(d, inplace=True), instead of update_(). Containers on storage backends lists this limit with the other limits of each backend.

Choose by need#

  • If your program chooses the keys at run time, use a TensorDict. See What is TensorDict?.

  • If you know the fields and want methods of your own and completion in your editor, use a TensorClass. See TensorClass.

  • If you want declared fields on an object that is a TensorDictBase, use a TypedTensorDict. It accepts state["key"] and **state, and a function that takes a tensordict accepts it. See TypedTensorDict.

  • If you stack items of different shapes, use lazy_stack(), which returns a LazyStackedTensorDict. See Stacking and variable-size data.

  • If your dataset is larger than the memory and is on a local disk, save a TensorDict with memmap_() and load it with load_memmap(). Its entries are then memory-mapped tensors. See Save and load tensordicts.

  • If your data is in HDF5 or Zarr files, use a PersistentTensorDict. See Large datasets and storage backends.

  • If several processes or machines must share the data through a server, use a TensorDictStore. See Large datasets and storage backends.

  • If you want typed fields on a file, a server, or a lazy stack, wrap it with from_tensordict of a TensorClass or a TypedTensorDict. See Containers on storage backends.

  • If your values have no common leading dimension, use a plain dict, or put them in a tensordict with batch_size=[].

TensorClass or TypedTensorDict?#

TypedTensorDict is experimental: its API can change in a minor release without a deprecation cycle (see TypedTensorDict). TensorClass follows the normal deprecation rules.

Both declare typed fields with class annotations, and both can wrap a tensordict of any backend. A TensorClass holds a tensordict, and a TypedTensorDict is one. The other differences follow from this:

Use TensorClass if:

  • Your fields include strings or other Python objects that you read as plain values.

  • You need a custom __init__, __post_init__, or the autocast flag.

Use TypedTensorDict if:

  • The object must be a TensorDictBase.

  • Your pipeline builds its state in stages and passes it on with **state.
